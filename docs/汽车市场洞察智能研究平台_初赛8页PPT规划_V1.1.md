## P2｜Why Now

# AI 正在重新定义数据的价值

### 核心判断

> **过去，数据价值受限于人的分析带宽；  
> AI 让同一份数据能够被更多次调用。**

### 左侧：传统模式

```text
数据
 ↓
分析师
 ↓
报表
 ↓
一次决策
```

### 右侧：AI / Agent 时代

```text
数据
 ↓
AI / Agent × 高频调用
 ↓
分析 / 验证 / 监控 / 研究
 ↓
持续决策
```

### 关键转折

但企业数据并不能天然被 AI 可靠调用：

- 数据分散
- 指标口径复杂
- 方法沉淀在人脑
- 结论难验证
- 每次研究都需要重新组织

### 三个乘数：从低频人工到高频系统

| 维度         | 传统（分析师）   | 系统化之后                     |
| ------------ | ---------------- | ------------------------------ |
| **调用频率** | 一年做 10 次分析 | 可以每天、每事件触发           |
| **研究广度** | 人工挑几个假设   | 系统扫描几十个方向             |
| **复用程度** | 一个分析师的方法 | 多个 Research App 可以持续调用 |

### 数据资产价值公式

> **数据资产价值 ≈ 数据质量 × 研究能力 × 调用频率**

同一份数据，质量越高、能被越可靠的方法调用、调用越频繁，产生的价值就越大。

mashang-service 提升的正是后两个乘数：

- **研究能力**：把分析师的方法沉淀为确定性算子与可验证 Research Flow
- **调用频率**：让同一套能力从"一年几次"变成"每天 / 每事件触发"

### 这一页只让评委记住一句话

> **AI 放大了数据价值，但企业真正缺的是“可持续调用的数据研究能力”。**

### Snowflake 的位置

Snowflake 只作为启发，不作为案例展开：

> AI 的价值不只是“分析更快”，而是让高质量数据被调用得更多。

### 建议时间

**35 秒**

## P3｜Innovation

# 我们的创新，不是让大模型做更多，而是明确哪些事情不该让大模型做

这一页不讲工程细节，只讲**技术原则**。

### 01｜语义资产化

**Data → Semantic Foundation**

> 解决：**AI 到底在调用什么数据？**

把：

- 数据
- 指标
- 实体
- 业务定义
- 车型代际
- 状态口径

从脚本中的隐性知识，变成统一语义底座。

目的不是“把数据整理得更漂亮”，而是：

> **让同一份数据能够被不同研究任务以同一口径持续调用。**

---

### 02｜方法算子化

**Analysis Method → Operator / Capability**

> 解决：**AI 到底用什么方法研究数据？**

把分析师脑中的方法沉淀为：

- 可重复执行
- 可测试
- 可复用
- 可审计

的确定性分析能力。

核心变化：

```text
分析师个人经验
      ↓
可复用研究方法
      ↓
Operator / Capability
```

目的不是“让 AI 自己算”，而是：

> **让已经验证过的方法可以被 AI 反复调用。**

---

### 03｜研究 Runtime 化

**Research Process → Runtime**

> 解决：**这些数据与方法怎样被持续、反复、可靠地执行？**

Runtime 不重新发明研究能力，而是负责：

```text
Context
→ Dispatch
→ Execute
→ Validate
→ Render
```

让数据、方法和研究流程形成稳定执行链路。

---

### 三个创新共同完成一件事

> ## **建立“数据资产 × 研究能力”的绑定机制。**

- **语义资产化** —— 让数据可以被可靠调用
- **方法算子化** —— 让研究方法可以被反复调用
- **研究 Runtime 化** —— 让调用可以持续、稳定、可验证地发生

因此：

> **企业真正需要沉淀的，不只有数据资产，还有与数据绑定的研究能力。**

AI 的价值，不是凭空创造研究方法，而是通过工程化把原本低频、依赖个人的研究调用，放大为高频、可复用的机器调用。

### 页面底部核心句

> **开放问题交给 AI，确定性计算交给代码，结果质量交给 Contract。**

### 这一页对应官方评分

- 技术独创性
- 先进性
- 关键突破

## P4｜Architecture

# 从 Agentic Loop 到 Research Runtime

**副标题：不是继续给 Agent 加能力，而是把能力沉到底层。**

这一页不只是展示“五层目录”，而是讲清楚一次真实的工程演进。

---

### Before｜Legacy Agentic Loop

第一阶段的思路是：

```text
LLM Planner
    ↓
Tool Router
    ↓
Agent Loop
    ↓
动态决定如何执行
```

实际工程中暴露出四个问题：

- **不稳定**：同类问题可能产生不同执行路径
- **难测试**：LLM 行为进入核心执行循环后难以稳定回归
- **口径易漂移**：业务规则可能被 Runtime 临时解释
- **Runtime 过重**：Planner、Router、Memory、业务逻辑逐渐耦合

因此没有继续给 Agent 增加能力，而是反过来：

> **减少 LLM 在确定性分析过程中的职责，把稳定能力沉到底层。**

---

### After｜五层 Research Runtime 架构

```text
1. Semantic Foundation
   dataset/ + shared/
        │
        ├─────────────────────────────┐
        │                             │
        ▼                             ▼
2. Base Capabilities          3. Daily Business Analytics Workspace
   capabilities/                 mashang_workspace/
   OCR / Search / Notify         日常业务分析工具箱
   Browser / Parse / Render      research → runtime → eval
        │                             │
        └──────────────┬──────────────┘
                       ▼
4. Unified Research Runtime
   mashang_runtime_v2
                       │
          ┌────────────┼────────────┬────────────┐
          ▼            ▼            ▼            ▼
5. Research Applications
        MIIT       auto_launch    nev_apeal    Project ...
```

---

### 能力下沉后的职责边界

底层沉淀：

```text
Schema
→ Operator
→ Capability
→ Contract
```

Runtime 本身只负责：

```text
Context
→ Dispatch
→ Execute
→ Validate
→ Render
```

也就是说：

> **Research Runtime 不负责“聪明地算答案”，而负责可靠地组织已有研究能力。**

---

### 工程演进证据

可作为页面右下角小 badge：

> **Legacy Agentic Loop → Runtime V2**

- 旧 Runtime 核心 Agentic Loop：**5,562 行**
- V2 核心确定性 Pipeline：**986 行**
- 核心执行代码减少约 **82%**
- Dispatch 转为 **config-driven**

注意口径：

> 986 行指核心执行 Pipeline，不等于整个 `mashang_runtime_v2/` 目录代码量。

---

### 三个系统关键词

- **Reusable**
- **Deterministic**
- **Verifiable**

---

### 这一页真正的 Takeaway

> **五层架构的本质，是把研究能力从 Agent 的临时行为，变成与数据资产长期绑定的工程资产。**

这样，Research Application 不再各自重新发明数据、方法和验证流程，而是持续消费同一套底层研究能力。

### 建议时间

**45 秒**


### Research / Market Analysis｜上市生命周期

**跨代际上市表现研究**

- 门店网络不同
- 非零售订单干扰
- 只能“感觉比上一代好”

After：

- 统一上市后 D1–DN 时间轴
- 自动代际归属
- 零售口径过滤
- 累积表现 / 单店效率 / 渠道信号交叉验证

**价值：从主观判断到可比研究**

**有效锁单当量**

After：

```text

        ↓

        ↓
逐单评分
        ↓
ELOE
```

输出：

- 有效锁单当量
- Backlog 有效率
- 风险暴露

**价值：经营数字从统计进入概率判断**

## P8｜Closing / Commercial Vision

### Snowflake 给出的启发

传统数据平台的价值主要来自：

```text
存储数据
→ 查询数据
→ 支撑少量人工分析
```

而 Agent / Research Runtime 让一次业务问题背后可能自动触发：

```text
检索
→ 查询
→ 比较
→ 代码执行
→ 再验证
→ 生成结论
```

因此真正被放大的，不只是“用户数”，而是：

> **每个用户 × 每天产生的数据与研究消费量**

---

### mashang-service 的商业逻辑

```text
更多业务用户
      ↓
更多 Research Task
      ↓
更多数据 / 方法 / Agent 调用
      ↓
更多 Research Run
      ↓
数据资产被更高频地消费
      ↓
研究价值持续释放
```

可以浓缩为：

> ## **数据资产价值 ≈ 数据质量 × 研究能力 × 调用频率**

其中：

- **数据质量**决定能不能用
- **研究能力**决定怎么用
- **调用频率**决定价值被释放多少次
- **AI / Runtime**把低频人工调用放大为高频机器调用

---

### 商业化启发

- Research Run
- 数据调用
- Agent / Runtime 执行
- 高级研究能力
- 专业 Research Application
- 私有部署与治理

---
