# 答辩口播全文：面向汽车市场洞察与经营决策的 Agent Harness 智能分析工作台

> 副标题：一个可被 Agent 驾驶的工程环境 / AI-native Analytics Workspace + Research Runtime

---

**【P1 · 封面】**

我的项目来自汽车市场洞察和经营分析的一线工作。

我想解决的问题是：企业真正需要沉淀的，不只有数据资产，还有与数据绑定、能够被持续调用的研究能力。

——这就是我要介绍的：一个面向汽车市场洞察与经营决策的 Agent Harness 智能分析工作台。它不是一个更快的报表工具，而是一个可被 Agent 驾驶的工程环境，是一套 AI-native 的分析工作区加研究运行时。

---

**【P2 · 提出一个好问题】**

过去我们经常强调，一个好的分析师最重要的能力之一，是能够"提出一个好问题"。

这当然来自深度思考、业务理解和经验。

但我在实际工作中越来越意识到，它还有另外一个原因：研究本身是有成本的，真正稀缺的是研究供给。

一个问题背后意味着找分析师、排期、取数、写代码、验证，最后才能形成报告。

所以过去我们必须在研究开始之前，就先判断什么问题最值得研究，把大量可能有价值的问题挡在研究入口之外。

但如果 AI 能够把研究供给扩大很多倍，我们的工作方式是不是也应该发生变化？

---

**【P3 · AI 对数据最大的改变】**

这也是为什么我认为，AI 对企业数据最大的改变，在于数据的使用方式。

过去，数据主要被做成 Dashboard 和 Report，再由人偶尔提出问题，它的价值天然受到人的分析带宽限制。

但是 AI 出现以后，一次人的提问，背后可以自动产生很多次查询、比较、计算和验证。

Snowflake 给了我很明确的启发：AI 的价值不只是分析更快，而是在增加核心数据资产本身的 consumption。

我总结了三个乘数：数据质量、研究能力、调用频率。

---

**【P4 · 三个动作】**

我的具体做法，可以概括成三个动作。

第一是语义资产化。把指标、实体、状态和业务定义，从人的经验和临时代码里抽出来。

第二是方法算子化。把已经被验证过的分析师经验和业务计算方法固定下来，变成可以测试、可以重复调用的 Operator 和 Capability。

第三是研究 Runtime 化。把这些能力统一组织、执行、验证和输出。

最终形成了现在这套五层架构。

目前它已经进入三类完全不同的汽车业务：MIIT 是工信部车型申报的产业情报研究；auto_launch 是新车上市和市场营销动态研究；nev_apeal 是大型新能源用户调研研究。

它们的数据和问题完全不同，但底层可以持续复用同一套研究能力。

---

**【P5 · Runtime 是从工作里长出来的】**

但这套 Runtime 并不是一开始就设计出来的。它的起点就是日常的工作。

不是写代码，而是让 Agent 发挥能力完成工作。而最重要的是，工作完成以后留下了什么。

如果一个方法在日常工作中被反复使用、验证有效，就应该从临时代码变成 Capability；如果一个业务口径反复出现，就应该变成 Schema；成熟以后再进入 Runtime。

所以 Workspace 是研究能力的生产现场，Runtime 是这些成熟能力的组织和调用方式。

---

**【P6 · 增量价值在哪里】**

那为什么 Agent 和 Runtime 做研究，会产生传统人工研究之外的增量价值？

我的答案并不是"Agent 比分析师更聪明"。

人真正擅长的是理解业务、判断什么重要、提出有价值的问题。

机器真正有优势的是研究的广度、重复次数和边际成本。

传统研究得到一个 Finding，往往就结束了。

但是 Runtime 可以继续追问：这个结论在哪些人群成立？边界在哪里？有没有反例？控制变量以后还成立吗？

所以一次 Research Run 不只消费一个问题，也会生产下一批问题。

AI 最大的优势，是把"继续研究"变得足够便宜。

但是研究供给如果扩大很多倍，错误也可能同步扩大。而这正好是计算机擅长的——看有没有置信度、有没有过拟合、有没有超出业务规则的范畴。

---

**【P7 · NEV APEAL 案例】**

NEV APEAL 项目是一份 9,937 × 370 的问卷数据集，我们提出的一个非常模糊的概念性问题：已经拥车的用户，会不会改变新能源用户对"升级感"的判断？

当然统计数据会告诉你是或不是，但这不应该是研究的终点，而是继续问：差异来自哪里？

进一步发现，这种差异主要来自外观、驾驶、动力和座舱，而补能差异很小。

于是又产生第三个问题：是不是因为配置更多，所以体验更好？

结果证据告诉我们：不是。配置数量本身不能解释这种体验差异。

于是问题再次递归：用户究竟是按照参数评价汽车，还是在评价实际体验有没有兑现原来的预期？

最终产生了新的研究空间——Expectation Calibration。

所以，同一份 9,937 × 370 的调研数据，没有在第一份报告之后结束，而是形成了 25 个 Discovery 视角、16 条 Research Runs 和 70+ Evidence。

Finding 不再是研究终点，而成为下一轮研究的入口。

Runtime 的价值不只是一次研究做得更快，而是一次研究会产生下一次研究。

---

**【P8 · 每一次研究留下什么】**

每一次 Research Run 结束以后，除了结论，系统到底留下了什么？

除了答案，一次研究可能留下新的 Schema，让业务定义更加完整；留下新的 Operator，把验证过的计算方法固定下来；留下新的 Evidence，成为以后研究可以直接引用的证据；留下新的 Contract 和 Eval，告诉系统这个结论在什么条件下成立、未来怎么验证。

所以每一次研究，实际上都在同时生产两种东西：Research Output 加 Research Capability。

这也是为什么工程上我后来反而减少了 LLM 的作用：开放问题交给 AI，确定性计算交给代码，结果质量交给 Contract。

会回答问题不是壁垒，能够让每一次回答都沉淀成下一次可以复用的研究能力，才开始形成企业研究基础设施。

Schema 越完整、Operator 越丰富、Evidence 越厚、Contract 越成熟，下一次研究的边际成本越低。

这就是我所说的研究复利。

---

**【P9 · 落地与终局】**

最后，这套能力首先服务于汽车 OEM、咨询和用户研究机构，以及企业内部的产品、市场和数据分析团队。

它带来的价值，不只是提高一次分析的效率，而是提升整个组织的研究供给能力：让更多问题可以进入研究，让成熟方法可以重复使用，把过去依赖个人经验的口径、方法和研究纪律，沉淀成组织资产。

从更大的视角看，我认为这也是 AI 时代释放数据要素价值的一种方式——让已有数据被更多人、更多次、高质量地调用。

汽车是我的第一个验证场景，未来希望从汽车市场研究工具，进一步走向企业级 Research Runtime。

让企业数据从静态资产，变成持续产生新决策认知的生产资料。
