# 一、V2 的核心变化

V2 不再按“技术能力清单”组织 PPT，而是按一个完整的因果故事推进：

> **你做了什么？ → 为什么需要？ → 为什么是现在？ → 怎么解决？ → 为什么更有价值？ → 真的跑出来了吗？ → 为什么可信？ → 最终有什么价值？**

整套 PPT 只围绕一个母题：

> **企业真正需要沉淀的，不只有数据资产，还有与数据绑定、能够持续调用的研究能力。**

AI 的作用不是凭空创造研究价值，而是：

> **把原本依赖个人、低频发生的研究调用，通过工程化放大为机器可以持续执行的研究能力。**

# 二、整套材料的三个核心记忆点

## 1. 数据本身不是最终资产，研究能力决定数据能被使用多少次

传统企业已经拥有大量数据，但数据价值长期受限于人的分析带宽。

真正决定数据资产价值的，不只是“有多少数据”，还包括：

- 研究能力是否存在；
- 研究方法能否复用；
- 数据能否被持续、高频调用。

## 2. Research Runtime 的核心，是把研究能力与数据资产绑定

它不是一个通用 Chatbot，也不是一个“更聪明的 Agent”。

它把：

- Semantic Foundation
- Operator / Capability
- Research Workflow
- Contract / Validation

沉淀成长期可调用的工程资产。

## 3. 一次研究不只产生一个结论，还产生下一次研究的能力

传统研究通常是：

```text
Question → Analysis → Finding → End
```

Research Runtime 则形成：

```text
Question
   ↓
Finding
   ↓
Boundary / Anomaly / New Hypothesis
   ↓
New Question
   ↓
Next Research Run
   ↺
```

因此：

> **传统研究产出是一份结论；Research Runtime 的产出，是“结论 + 下一次研究的能力”。**

## P3｜Why Now

# AI 让数据从“被阅读”走向“被调用”

### 这一页只回答

> **为什么现在值得重新做这件事？**

### 传统 BI

```text
Data
 ↓
Report / Dashboard
 ↓
Human
 ↓
偶尔提出问题
```

数据价值受限于人的分析带宽。

### AI / Agent 时代

```text
Human
 ↓
AI / Agent
 ↓
查询 → 检索 → 比较 → 计算 → 再验证
 ↓
Data 被反复调用
```

一次业务提问背后，可以自动触发多次数据和计算调用。

### 三个乘数：AI 改变的不只是效率

| 维度 | 传统研究 | Runtime 化以后 |
|---|---|---|
| **调用频率** | 项目制、低频调用 | 每天 / 每事件 / 持续触发 |
| **研究广度** | 人工挑少数问题 | 系统可以扫描更多假设 |
| **方法复用** | 方法依附分析师 | 方法沉淀后跨任务调用 |

### 数据资产价值公式

> ## **数据资产价值 ≈ 数据质量 × 研究能力 × 调用频率**

解释：

- **数据质量**：决定能不能用
- **研究能力**：决定怎么用
- **调用频率**：决定价值被释放多少次

AI / Runtime 重点放大的，是后两个乘数。

### Snowflake 的位置

只作为外部启发，不展开公司介绍：

> **AI 的价值不只是“分析更快”，而是让高质量数据被调用得更多。**

### 这一页最终 Takeaway

> **AI 不只是让一个问题回答得更快，而是让组织有能力研究原本不会被研究的问题。**

## P5｜Mechanism

# Runtime 为什么让同一份数据产生更多价值？

### 这一页只回答

> **同一份数据，为什么经过 Runtime 以后价值会变大？**

这一页是整套 PPT 的“机制页”。

核心讲两个机制。

### 机制 1｜Research Compounding
#### 一次研究会生产下一次研究空间

传统研究：

```text
Question
   ↓
Analysis
   ↓
Finding
   ↓
End
```

Runtime 化研究：

```text
Question
   ↓
Finding
   ↓
Boundary / Anomaly / New Hypothesis
   ↓
New Question
   ↓
Next Research Run
   ↺
```

### 核心句

> **一次 Research Run 不只消费一个问题，也会生产下一批问题。**

因此同一份数据不会因为“一份报告已经完成”就被研究完。

一次研究还可能产生：

- 新 Hypothesis
- 新 Segment
- 新 Boundary
- 新 Confounder
- 新 Analysis Type
- 新证据需求

### 机制 2｜Governance
#### 研究空间扩大，但错误不能同步放大

如果 AI 可以研究更多问题，就必须回答：

- 什么能讲？
- 什么不能讲？
- 什么暂时无法回答？

因此 Runtime 同时需要：

```text
Evidence
→ Qualification
→ Stop-check
→ Contract
→ Validation
```

最终形成三种状态：

- **READY**
- **REJECTED**
- **INCONCLUSIVE**

### 这一页核心结论

> **Research Runtime 同时扩大研究空间，并约束研究边界。**

进一步：

> **传统研究的产出是一份结论；Research Runtime 的产出，是结论 + 下一次研究的能力。**

### 建议视觉

左右双机制：

左：递归 Research Loop  
右：Governance Gate

底部用一条大结论把两边连接。

### 建议时间

**40 秒**

## P7｜Engineering Innovation

# 把“会分析”变成可重复、可验证、可审计的工程能力

### 这一页只回答

> **为什么它不是普通的 AI + Excel / RAG / Agent？**

### 研究能力必须工程化

传统 AI 分析工具的核心能力通常是：

> 能回答问题。

而企业 Research Runtime 要求的是：

> **同一个问题，下次还能按同样口径重新跑；系统升级以后还能验证结果没有漂移。**

### 七类可信研究工程

#### 1｜Dataset / Schema
统一：

- 指标
- 实体
- 状态
- 业务定义

解决：

> **到底在分析什么？**

#### 2｜Operator
确定性执行关键业务计算。

解决：

> **关键数字不能由 LLM 临时解释。**

#### 3｜Capability
把分析方法封装为可复用研究能力。

解决：

> **一个方法如何跨问题、跨应用重复使用？**

#### 4｜Result Contract
统一：

```text
status
scope
result
followup_context
warnings / errors
```

解决：

> **不同能力的输出如何被机器继续消费？**

#### 5｜Evidence / Provenance
记录数字、结论与来源。

解决：

> **结果从哪里来？**

#### 6｜Qualification / Stop-check
明确：

- READY
- REJECTED
- INCONCLUSIVE

解决：

> **系统什么时候应该停止讲故事？**

#### 7｜Eval
Golden Case / Numeric Eval / Render QA。

解决：

> **系统升级以后，如何确认研究能力没有退化？**

### 工程演进：从 Agentic Loop 到 Research Runtime

这段放在 P7，而不是挤在 P4。

#### Legacy

```text
LLM Planner
→ Tool Router
→ Agent Loop
→ Dynamic Execution
```

实际问题：

- 不稳定
- 难测试
- 业务口径易漂移
- Runtime 过重

#### V2

```text
Context
→ Dispatch
→ Execute
→ Validate
→ Render
```

工程证据：

- Legacy Agentic Loop：**5,562 行**
- V2 核心确定性 Pipeline：**986 行**
- 核心执行代码约 **-82%**
- Dispatch：**config-driven**

### 页面核心句

> **我们的创新不是让大模型做更多，而是找到哪些事情不应该让大模型做。**

职责边界：

> **开放问题交给 AI，确定性计算交给代码，结果质量交给 Contract。**

### 最后一句

> **会回答问题 ≠ 可作为企业研究基础设施。**

### 建议时间

**50 秒**
