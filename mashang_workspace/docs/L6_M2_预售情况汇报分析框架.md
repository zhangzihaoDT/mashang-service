# L6 M2 预售情况汇报：数据结构与分析框架

> 文档类型：预售期分析方案与数据资产说明  
> 数据快照：截至 2026-08-24（以文件实际最大日期为准）  
> 目标对象：L6 M2，即业务定义中的 `DM2`

## 1. 分析目标与边界

本报告回答五个问题：

1. **订单**：预售订单规模、订单阶段、车型/能源/地区结构如何？
2. **下发线索**：线索规模、渠道结构和成熟度如何？
3. **正反向对比**：从线索到订单的正向转化，与从订单回溯线索来源的反向归因是否一致？
4. **预选配置**：用户选择了哪些版本、颜色、内饰和智能化配置？
5. **订单用户画像**：锁单/订单用户的年龄、性别、地域和支付特征是什么？

本报告是分析框架，不预先填充业务结论。所有结论须附数据源、时间窗口、筛选条件和指标口径。

### 1.1 L6 M2 的统一识别口径

使用 `shared/schema/business_definition.json` 中的 `series_group_logic.DM2`：

```text
product_name 同时包含「一代」和「L6」
或 product_name 同时包含「L6」和「M2」
或 product_name 包含「Jimmy Choo」/「JimmyChoo」
```

不要仅使用 `series='L6'`，否则会混入 DM0/DM1；不要仅使用产品名中的 `M2`，否则会漏掉正式名称为“全新一代智己L6”的订单。

业务定义中的 DM2 预售窗口为 **2026-08-18 至 2026-09-18**，预计成熟日为 **2026-10-31**。本次快照截至 2026-08-24，属于预售早期，7 日/30 日转化和最终锁单规模均存在右删失。

## 3. 五部分汇报框架

### 3.1 订单：预售规模与订单质量

**核心问题**：预售订单是否形成规模，订单从小订到锁单的推进是否顺畅，结构是否符合产品预期？

**建议页面与指标**：

| 页面 | 核心指标 | 分组维度 | 数据源 |
|---|---|---|---|
| 订单总览 | 订单数、去重订单数、小订数、大定数、锁单数、开票数、交付数 | 原始订单池 / 排除试驾车订单池 | `order_data.parquet` |
| 日趋势 | 日订单创建、日小订、日大定、日锁单 | 日期 | `order_create_date`、各阶段时间 |
| 产品结构 | 订单量及占比 | `product_name`、版本、能源类型、电池容量 | `product_name` + 车型映射 |
| 区域结构 | 订单量、占比、城市集中度 | `store_city`、`license_city`、省份、城市线级 | 订单表 + 城市映射 |
| 订单推进 | 小订转大定、大定转锁单、锁单转开票、开票转交付 | cohort/订单创建日 | 订单阶段时间 |

**统一口径**：

- 订单数：`COUNTD(order_number)`，按 `order_create_date` 统计。
- 小订数：`intention_payment_time` 非空。
- 大定数：`deposit_payment_time` 非空。
- 锁单数：`COUNTD(order_number WHERE lock_time IS NOT NULL)`，不能用订单创建日期代替。
- 开票数：`invoice_upload_time` 非空；交付数：`delivery_date` 非空。
- DM2 预售订单在锁单前 `order_type` 为空属于正常业务状态，不作为排除条件。订单分析以 DM2 产品范围和订单阶段时间为准；锁单后再按已形成的 `order_type` 做状态拆分。

**建议图表**：订单阶段漏斗、日订单/锁单双轴趋势、版本结构堆叠柱、城市 Top 20 横向条形图。

### 3.2 下发线索：规模、渠道与成熟度

**核心问题**：线索从哪里来，门店承接能力如何，早期线索是否正在释放为试驾和锁单？

**建议页面与指标**：

| 页面 | 指标 | 口径 |
|---|---|---|
| 线索总览 | 总下发线索、门店线索、下发门店数、渠道覆盖率 | 对 `assign_data.csv` 按日期求和或加权汇总 |
| 渠道结构 | 门店、平台、直播、APP 小程序、快慢闪线索量及占比 | 各渠道线索列 / 总下发线索 |
| 线索效率 | 当日试驾率、7 日试驾率、当日门店锁单率、7 日锁单率、30 日锁单率 | 分子除以对应下发线索数 |
| 释放成熟度 | D0、D7、D30 锁单释放 | 以 `Assign Time` 为 cohort，使用已成熟 cohort 或预测曲线 |
| 运营承接 | 线索/门店、锁单/门店 | 与在营门店数结合时，明确 30 日活跃门店定义 |

**分析边界**：`assign_data.csv` 没有车系、车型、订单号或线索 ID，因此不做 L6 M2 车型级线索转化率细分，而是观察预售窗口期整体业务转化情况。汇报时将 L6 M2 预售订单趋势与同期整体业务线索转化率放在同一时间轴，判断 M2 预售期间整体转化率是否发生变化。

线索模块应比较预售窗口前基线、窗口内每日/每周变化，以及窗口结束后成熟 cohort 的 7 日/30 日结果。未成熟 cohort 只展示当前观测值，不把尚未发生的转化当作最终结果。

**建议图表**：渠道结构 100% 堆叠图、渠道 7/30 日锁单率对比、cohort 释放曲线、日线索与日锁单滞后趋势。

### 3.3 正反向对比：竞争 PK 正反向排名

正反向对比使用**竞争 PK 数据**（`业务数据记录_竞争PK（正反向排名）.csv`），不采用订单-线索逐单归因作为主口径。

#### 口径

- 数据源：`业务数据记录_竞争PK（正反向排名）.csv`，取 `series=L6` 的周度记录。
- 字段：`Week`、`车系`、`品牌`、`PK次数`、`PK正向排名`、`PK反向排名`。
- PK 正向排名 = 竞品对本品（L6）的竞争冲击强度排名；PK 反向排名 = 本品对竞品的影响排名。排名越小越强。
- 最新周一般为报告日所在周（本报告使用 **2026-08-17 ~ 08-23**）。

#### 输出

- L6 最新周竞品 PK 榜（PK次数、正反向排名）。
- 上汽集团/重点竞品（如 MG 07 EV、尚界 Z7）近若干周 PK 趋势。
- 判断：正向冲击最强竞品、上汽内部竞品对 L6 的压力、反向影响较弱/较强的车型。

#### 说明

- 订单-线索逐单归因（`main_lead_id` → `lc_main_code`）匹配率低（约 14.8%），不作为正式口径，仅在需要渠道来源补充时在附录呈现。
- PK 数据与订单漏斗是两个不同口径，不得直接换算。

### 3.4 预选配置：从订单配置长表还原用户选择

**核心问题**：用户优先选择哪些版本和配置，付费选装与标配结构是否符合产品假设？

`config_attribute.parquet` 是订单-属性的 EAV 长表：同一订单对应多行配置记录。分析前必须先筛订单，再按订单去重聚合，不能直接对行数做比例。

**建议页面与指标**：

| 页面 | 指标 | 维度 |
|---|---|---|
| 版本选择 | 订单数、占比 | `product_name` 及业务版本映射 |
| 配置拥有率 | 拥有配置的订单数 / 对应订单数 | `Attribute`、`value_code` |
| 颜色与内饰 | 各款式订单数、占比 | 外饰、内饰、轮毂、方向盘 |
| 智能化配置 | 激光雷达、智驾、座舱等拥有率 | 配置分类、选装档位 |
| 价格结构 | 选装金额、选装包渗透率 | `price`、配置包 |

**配置口径**：

- 配置唯一稳定标识为 `(Attribute, value_code)`；`value` 只作为显示名。
- `value_code` 缺失时，按 `config_semantics.json` 的 display/aliases 归一；不能简单按显示文本拼接。
- “拥有率”分母为有效订单数，不是配置表行数。
- `required`、`option_flag`、`price` 用于解释标配/选装和金额，不直接作为拥有判定。
- LS8 的“已选”规则是车型特例，不应未经验证套用到 L6 M2。

**当前数据结论**：`config_attribute.parquet` 原缺少 DM2 是因为重建脚本只合并年度快照、未合并 Tableau 增量 `config_attribute_data_update.csv`（该增量已含 227 个 DM2 订单）。已将增量合并重建（2026-08-24），DM2 覆盖提升至 227 单（7.8%）。当前渗透率基于有配置记录的样本内订单，覆盖不足时明确标注样本范围，不以其他车型配置替代，也不编造 L6 M2 配置渗透率。

### 3.5 订单用户画像：识别真实下单人群

**核心问题**：L6 M2 的订单用户是谁，是否集中在特定年龄、性别、城市和支付方式？

**建议页面与指标**：

| 画像维度 | 字段/派生逻辑 | 输出 |
|---|---|---|
| 年龄 | `buyer_age`、`owner_age`；缺失率单列 | 均值/中位数、年龄段分布、代际分布 |
| 性别 | `buyer_gender`、`owner_gender` 对应实际字段为 `order_gender`、`owner_gender` | 性别占比及缺失率 |
| 地域 | `license_city`、`store_city`、省份/城市线级映射 | Top 城市、城市线级、区域集中度 |
| 购车角色 | buyer 与 owner 字段对比 | 本人购车/代购或登记人差异 |
| 支付方式 | `final_payment_way`、`finance_product` | 全款/金融/其他结构 |
| 订单状态 | 小订、大定、锁单、退订时间字段 | 不同人群的推进率和退订率 |
| 交付状态 | `invoice_upload_time`、`delivery_date` | 已开票/已交付人群画像 |

画像报告以 L6 M2 订单数据为唯一主体，至少拆分三组：原始预售订单、排除试驾车后的订单、已锁单用户。样本量不足时只展示绝对数，不进行过度细分。

`audience_research/lock-attr-2026画像数据.csv` 不作为本次 L6 M2 用户画像的数据源；如需参照历史人群，只能在附录中作为外部基准，并明确标注不是 L6 M2 当前订单画像。

## 4. 推荐的数据模型与处理流程

### 4.1 逻辑模型

```text
订单事实表
  order_number
  product_name → DM2
  各阶段时间 → 订单漏斗
  main_lead_id → 线索归因
  buyer/owner 字段 → 用户画像

线索日聚合表
  assign_date
  channel
  lead_count / test_drive / lock_7d / lock_30d

配置事实表
  order_number
  Attribute + value_code
  price / required / option_flag

归因事实表
  lc_main_code
  small_channel
  lock_time
```

### 4.2 执行顺序

1. 固定快照日、预售窗口和 DM2 识别规则。
2. 建立订单范围表，保留 `scope_flag`、`order_type`、排除原因和来源文件。
3. 先输出订单总览，再输出线索聚合，避免先做比例后发现分母不一致。
4. 做正向/反向连接审计，输出匹配率、重复率和未归因率。
5. 配置表按订单号关联，先验证覆盖率，再计算配置拥有率。
6. 用户画像按订单去重，单独报告字段缺失率。
7. 通过成熟度校正、时间窗口一致性和业务口径复核后生成汇报页。

## 5. 最终汇报建议结构

1. **一页结论**：订单规模、线索规模、正反向差异、配置数据状态、用户画像关键词。
2. **订单**：订单阶段漏斗、日趋势、版本/能源/区域结构。
3. **下发线索**：总量、渠道结构、试驾与 7/30 日锁单释放。
4. **正反向对比**：线索聚合转化 vs 订单逐单归因，附连接质量说明。
5. **预选配置**：版本、颜色、内饰、智能化配置和选装金额；若覆盖不足则展示数据缺口。
6. **订单用户画像**：年龄、性别、地域、支付方式和订单推进差异。
7. **口径与附录**：字段映射、过滤规则、时间窗口、缺失率、数据质量检查。
